# Agent Note: 发现类页面（联想词／热搜／作者主页／排行榜／评论回复／章节预览）

Status: implemented

## Problem

`` 注册了 35 个端点，而 fqapp 只用了 12 个。差集里是**后端已经就绪、客户端完全没用**的能力：搜索联想词、热搜榜、作者信息、排行榜、评论回复、章节摘要。官方客户端都有对应入口，fqapp 里则完全没有落地 —— 对比官方截图时最明显的空白。

这不是「要不要做」的问题，而是「数据到底拿不拿得到」的问题。前几轮的教训（演员表要新端点、章评在另一个服务、角标被首页链路丢掉）说明：**看着能做的功能常常卡在上游数据**。所以这次先把 6 个端点逐个实测，确认返回真实数据后再动手；实测中三项与预期不符，正是本文要记下来的部分。

## Decision

6 项各接一个已有的  端点，全部**只加客户端代码**，不动后端、不改 `LEGACY_COMMIT`。

| 功能 | 端点 | 落点 |
|---|---|---|
| 搜索联想词 | `GET /api/v1/search/suggest?q=` | 搜索页输入防抖下拉 |
| 热搜榜 | `GET /api/v1/search/hot` | 搜索页空态 |
| 作者主页 | `GET /api/v1/authors/{id}` | 新建 `AuthorPage`，详情页作者行进入 |
| 排行榜 | `GET /api/v1/rank/{id}` | 新建 `RankPage`，首页 hero 进入 |
| 评论回复 | `POST /api/v1/comments/{id}/replies` | 书评展开 |
| 章节预览 | `GET /api/v1/books/{id}/chapters/summary` | 详情页目录预览块 |

## 上游契约（实测，与预期不符的三处已标注）

### 作者作品来自 `author_book_info`，不是 `bookshelf` ⚠️

这是本次最容易踩错的一处。`GET /api/v1/authors/{id}/bookshelf` 听起来就是「该作者的全部作品」，实测**不是**：

- 返回 `total=126`，但 30 条里 **30 个不同的 `author_id`**、30 个不同的 `author` 名；
- `bookshelf_tab` 是 `都市日常 / 都市脑洞 / 都市高武 / 玄幻脑洞 / 豪门总裁`。

也就是说它是**按分类聚合的书单**，与请求的作者无关。真正的作者作品在 `author_info` 响应的 `author_book_info` 里（该作者 4 部，作者名一致，带 `word_number`／`abstract`／`thumb_url`／`read_count`）。

若照名字接了 bookshelf，作者页会显示 126 本**别人的书**。因此 `AuthorProfile` 只读 `author_book_info`，`bookshelf` 端点未使用。

### 榜单目录在首页响应里，字段名与猜的不同 ⚠️

排行榜没有「取榜单列表」的端点。目录藏在首页小说流的**榜单卡片**上：

- 榜单卡片：`cell_name = "排行榜"`，`cell_id_str = 7098235271900037133`；
- `rank_with_category_data.rank_algo_list[]`（**不是 `rank_list`**）给出榜单：`推荐榜101 / 完本榜100 / 巅峰榜200 / 新书榜108 / 漫剧榜550 / 短剧榜502`；
- `rank_with_category_data.sub_info_list[]` 给出分类：`全部0 / 穿越37 / 系统19 / 都市1 …`（16 个）。

`rank_algo` 回传为 `algo_type`，`info_id` 回传为 `rank_sub_info_id`。

**2026-09-12 补：当时「实测可正确切换榜单与分类」的结论是错的。** 端点参数确实对（只有 `algo_type=200` 巅峰榜返回真实内容，其余 algo 返回 30 个空分组），但 `parsePage` 从没匹配过响应形状：榜单页的 `cell_view.cell_data[]` 是**分组单元**（月榜 / 男生榜 / 女生榜），作品在第二层 `cell_data[].book_data`，而解析器只扒了一层、把分组单元当作品单元找 `book_data`，自然全军覆没 —— 所有榜单一直显示「该榜单暂无内容」。这类「`code=0` 但页面为空」又一次不是接口问题，而是形状假设错了；修复是解析时先看本层 `book_data`，没有就下钻一层 `cell_data`。教训同 39 通道与段评版本：**验证「接口通」必须跑应用自己的解析器拿到条目，只看 `code=0` 不算数**。

**`rank_id` 必须是真实的榜单卡片 id**（`cell_id_str`）。用占位值不行：`rank/1?algo_type=200` 返回 `code=0` 但 **0 本书**（静默失败），`rank/0` 报 `100103`。所以 `RankCatalog` 一定要把卡片 id 一起解析出来，不能只留榜单名与 algo。

### 章节 `summary` 返回的是正文开头 ⚠️

字段名是 `summary`（ 注释也写作 AI 摘要），实测 `summary_item_data[0].summary` 是**该章的正文片段**，例如：

> “对不起......”“老子是兔子啊，特么全是素！”耳边传来稀奇古怪的声音，张晨缓缓睁开眼......

对一个能直接读正文的 App，把它当「AI 摘要」展示是误导。因此 UI 明确按**试读预览**呈现（`_ChapterExcerpt`，截 3 行），只在详情页的 3 章预览块里取一次（一次请求带 3 个 `item_ids`）。

### 回复体在 `Common`（大写 C），三个参数必填

- 路径：`POST /api/v1/comments/{comment_id}/replies`；
- **`comment_id` / `group_id` / `book_id` 三者均为必填**，缺一即 400（实测只传 `comment_id` 撞了 400）；书评场景下 `group_id == book_id`；
- 每条回复的正文与作者在 `reply_list[].Common.content.text` 与 `Common.user_info.base_info`，**大写 `Common`**（与段评服务同一习惯）；点赞数在 `reply_list[].stat.digg_count`。

### 热搜词两层嵌套

`data[].search_tag_data[].tag_title`，且 `data` 里存在**没有任何词的 cell**，必须容错跳过；实测 2 个 cell 共得到 2 个词。

## UI 取舍

### 作者行不再假装能关注

详情页作者行原本有一个 `关注` 按钮，但 `onFollow` 默认是 `() {}` —— **点了没有任何反应**，是个死控件。后端没有关注端点（`can_follow` 只是上游的一个标志位），所以没有把它接成真按钮的选项。

改为一个**能真的工作**的入口：整行可点 + 尾部 `主页 >`，进入作者主页。文案也从「关注我，掌握书籍最新动态」改成「查看作者主页和全部作品」。

### 离线规则照旧

新加的 6 个 loader 全部沿用「注入过 loader 即视为离线」：详情页的回复与预览 loader 在 `detailLoader` 或 `directoryLoader` 被注入时返回 `null`（即不显示该功能），搜索页的联想与热词同理。这样测试与预览不会偷偷访问网络。

## Alternatives considered

- **作者页用 `/authors/{id}/bookshelf`**：名字最像「作者的全部作品」，但实测是分类书单，30 条里 30 个不同作者。否掉，改用 `author_book_info`。
- **排行榜只放榜单名、用固定 `rank_id`**：少解析一个字段，但实测占位 id 静默返回 0 本书，页面会永远空白且看不出原因。因此坚持从卡片解析 `cell_id_str`，并加测试锁死。
- **把 `summary` 当「AI 章节摘要」展示**：字段名支持这么做，但内容是正文开头，会误导用户以为是机器生成的梗概。改为按试读预览呈现并截断。
- **回复改成一次预取全部书评的回复**：一次请求换省事，但书评列表很长而多数不会被展开，且上游有 `count` 上限。改为**点击时懒加载**（有测试断言首次渲染时 `calls == 0`）。
- **热搜词不做容错、直接取 `data[0]`**：实测存在空 cell，直接取会漏词或崩。改为遍历所有 cell 并去重。
- **把详情页的 `关注` 接成一个假的本地状态切换**：能让按钮「看起来有反应」，但用户会以为真的关注了。否掉，改为可用的主页入口。
- **给这 6 项各写一篇 Note**：会让读者在 6 篇之间跳。它们共享同一个决定（「用差集里已就绪的端点补齐发现类入口」）与同一批契约事实，因此合为一篇，代码入口的反向注释都指向本文件。

## Consequences

- 搜索页有了联想词与热搜（此前全仓库 `suggest|predict|autocomplete` 命中 0），搜索从「盲打关键词」变成有引导。
- 详情页的作者行从**死按钮**变成可用的作者主页入口；作者页展示简介、等级（`作家Lv.5`）、粉丝数（`2.1万粉丝`）与全部作品。
- 新增排行榜页：6 个榜单 × 16 个分类，支持翻页且**续页编号连续**（第 2 页从 31 开始，不重置为 1）。
- 书评可展开回复；回复懒加载，失败只在该条下提示「回复加载失败」，不影响列表。
- 详情页目录预览块每章多一行正文开头，**一次请求**覆盖 3 章。
- 搜索页每次首屏会多一次热搜请求（失败静默）；联想词按 250ms 防抖，并带 `_suggestGeneration` 防止迟到响应覆盖新查询。
- 模型命名：排行榜条目页类型叫 `RankBoard`（不是 `RankPage`），避免与页面类 `RankPage` 冲突。
- `AuthorProfile.followerLabel` 在粉丝数为 0 时返回空串：「0粉丝」是噪音。

### 实现期间自己引入并修掉的两个缺陷

两处都不是预先存在的 bug，而是这次改动带出来、被自己的测试当场抓到的：

1. **搜索联想面板会在结果页上残留**。`_search()` 只更新了 `_query` 而没更新 `_draft`，而面板的显示条件是 `_draft != _query`。点选一条联想词（如 `修仙精品小说`）时输入框里还是 `修仙`，于是面板盖在刚搜出的结果上。修法：`_search()` 同时同步 `_draft` 并清空 `_suggestions`、递增 `_suggestGeneration`。
2. **排行榜空目录的「重试」是空操作**。错误视图原本只调 `_loadFirst()`（重取榜单条目）。当失败的是**目录本身**时没有榜单可重取，点重试毫无反应。修法：重试改调 `_bootstrap()`，重跑整个引导流程。
