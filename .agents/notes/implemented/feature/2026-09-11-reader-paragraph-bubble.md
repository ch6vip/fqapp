# Agent Note: 阅读器正文内联段评气泡

Status: implemented

## Problem

段评此前只在阅读器菜单里有一个「段评 · N」入口，点开是**按段落分组的底部面板**。正文本身没有任何标记：读者读到一段有话想说的地方，看不出这段有没有人评过，必须先收菜单、找入口、再在面板里翻到那一段。

官方客户端是在正文里直接画气泡的，这也是用户这次要的效果。

2026-09-12 用户在《游戏入侵：开局金刚明王功》（现名《神域囚徒！》）第 1 章反馈所有气泡消失。手机内实际运行的 JNI 后端落后于桌面验证所用的源码；此外，旧图文缓存可能保留了正文却没有上游段落编号。两条链路都能让正文正常、气泡静默消失，不能只验证桌面接口或 Flutter 布局。

需要先说明的是：本文推翻了自己上一篇结论。[章评／段评端点](2026-09-10-chapter-ideas-endpoint.md) 当时把内联角标列为**否掉**的方案，理由是「需要改动分页布局逐行的命中测试，风险高于收益」。这次做了，做法与当时的顾虑不同——见下。

本文随后又推翻了自己的**第一版实现**（门槛与气泡外观都错了），那部分作为「踩过的坑」保留在下面，因为它正是真机反馈暴露出来的。

## Decision

在段落**末行末尾**内联一个**空心圆圈**气泡，圈内是段评数，点它直接打开该段的段评面板。

### Android 包里的后端版本必须实际核对

`/api/v1/chapters/7590221427400262168/reviews?comment_source=3` 在桌面 `127.0.0.1:8080` 返回段评计数，但通过 ADB 转发到手机的 `127.0.0.1:18080` 返回 `缺少book_id参数`。旧 JNI 库把章节 reviews 路由到了书评，`ApiClient.chapterIdeas` 的容错把这个错误变成空列表，所有气泡随之隐藏。

旧 `liblegacy.so` 的 Go 构建信息为 `148e2dedc1cbe24507b269a32d11a802e8c46a44`。使用 CI 已固定的 `f66712208c305c1c24b98cb4231b9601f7514ea1` 干净源码编译 Android ARM64 JNI 库，该版本将章节 reviews 路由到 `idea_list`。无需修改后端源码；必须替换 `android/app/src/main/jniLibs/arm64-v8a/liblegacy.so` 后重新打包。构建使用本地独立 clone，保留原后端工作区的未提交内容；本机 Go 1.26.7 的 VCS 扫描忽略 worktree 的 `.git` 文件，嵌套 worktree 会误写外层应用仓库的版本，因此不采用那份元数据错误的构建产物。

安装前从 APK 中提取 JNI 库核对 SHA-256 和 Go 构建信息，安装后通过 ADB 转发检查手机后端。APK 签名和 ZIP/ELF 对齐通过，只能证明包可安装，不能证明内嵌后端具备最新路由。

### 旧缓存按需补齐真实段落编号

`ChapterContent` 的版本 2 缓存增加可选字段 `paragraphIdsChecked`：解析原始 HTML 后为 true，纯文本降级为 false。旧缓存没有此字段时，根据是否保留过明确的 `idx` 判断；有插图检查标记但没有编号的旧缓存仍需升级。去掉首行标题和缓存往返均保留此状态。检查过的 HTML 即使没有编号也保持 true，避免每次打开都重复请求。

`ReaderPage._loadIdeas` 收到正数评论计数后，发现编号尚未检查时，复用已有去重的 `_refreshCachedChapter` 请求原始正文。刷新后更新内存与磁盘缓存并重排，继续沿用原有文字位置迁移；失败时保留可读正文。没有评论时不为编号单独请求正文。官方 `DefaultResourceCallback` 明确检查 `GetPIdx() < 0`，段评 presenter 使用 `getEndParaId()`；这里同样只使用真实 `<p idx>`，不按显示顺序编造编号。

### 评论正文：卡了很久，根因是一个枚举值

**第一版认定「取不到」，这是错的。** 当时的推理是：官方 presenter（`ParaCommentListPresenter` 构造器）把 `server_channel` 设成 43，照抄之后 `code=0` 但恒 `total=0`，于是判断为"匿名设备被限制"。真机反馈「面板里应该有内容」迫使重查，才找到真正的根因。

**`server_channel` 必须是 39（`NovelShortStoryParaList`），不是官方 presenter 里的 43。**

| 试验 | 结果 |
|---|---|
| `server_channel=43`（照抄 presenter） | `code=0`，**total=0** |
| **`server_channel=39`** | **`code=0`，total=5**（与该段 idea 计数一致） |
| 33/34/35/36/45/28/14/8 | `103001` 被拒 |
| 去掉 `item_version` | `103001` |
| 去掉 `para_index` / `book_id` / `group_type` / `comment_type` / `comment_source` | `103001` |

实证：同一段 idea 列表报 `count=5`，`server_channel=39` 恰好返回 5 条；`para_index=0` 报 24 条时返回 20 条 + `has_more=true`。

**2026-09-12 二次修正：39 也是部分命中，真正的段评通道是 38。** 真机读《我不是戏神》第 1 章第 0 段（计数 77519）时面板显示「暂无评论」——39 通道对该书返回 `code=0, total=0`，与当年 43 的症状一模一样。逐通道重扫发现 **38 对所有测过的书都返回与 idea 计数严格一致的数据**（含当年验证 39 的两本书：523、795 分毫不差），且 cursor 翻页正常；39 只是恰好镜像了当时那两本书的数据。这次的症状链条和 43、39 两轮完全同构：`code=0` + `total=0` ≠ 没有评论，**只要计数接口有数而列表接口为空，先怀疑通道/参数，别怀疑数据**。

有意思的是，43 正是从官方 `ParaCommentListPresenter` 里读出来的，而它对我们无效 —— 这与 [章节评论端点](2026-09-10-chapter-ideas-endpoint.md) 的教训一致：**反编译能给出配方，但配方对不对必须用真实响应验证**。当时正是因为 `code=0` 看起来"请求被接受了"，才误判成权限问题；实际上"被接受"与"有数据"是两回事。

拿到正文的关键参数一共五个，缺任一即 `103001`：`book_id`（真实书 id）、`group_id`（**章节** item_id，不是书 id）、`para_index`（`<p idx>` 值）、`item_version`（章节版本）、以及上面那个 `server_channel=39`。

### 章节版本必须一路带到阅读器

`item_version` 来自**目录**响应（`item_data_list[i].version`），正文和详情都没有。阅读器的 `Chapter` 模型保留这个字段，并在缓存里持久化。旧缓存恢复为空串时，先采用段评计数响应中的版本；该响应也没有版本时，`ApiClient.paragraphComments` 按书 ID 刷新目录，再按章节 item ID 找版本。仍然拿不到版本时抛出可重试的加载错误。不能直接返回空列表，否则会出现「气泡显示有评论，点开却说没有评论」。

**2026-09-12 补：上面的目录兜底曾整个失效，因为应用实际读的是 `/api/directory` 桥接端点，验证时打的是 `/api/v1/books/{id}/directory`。** 两个端点的形状不同：桥接响应里规范化后的 `data.data.chapterListWithVolume` 条目只有 `itemId/title/volume_name`，**没有 `version`**；带版本的上游原始 `item_data_list` 就在同一响应的 `data.item_data_list`，解析器却没读它。于是所有从目录解析出的 `Chapter.version` 都是空串——目录兜底"找到了 870 章、每章版本为空"，仍然抛错，面板显示「评论加载失败」。上游还会回声空版本（`chapterIdeas` 不带 `item_version` 请求时，部分章节的 `data.item_version` 就是 `''`），所以段评计数响应里的版本也指望不上。修复：`parseDirectory` 从同一 payload 里找到原始 `item_data_list`，按 `item_id` 把版本合并进所有缺版本的章节。**教训与 39 通道那节相同：验证配方时用的端点必须就是应用运行时调用的那个**——`/api/v1/books/...` 上验证通过不代表 `/api/directory` 上成立。

补字段时发现一个**既有缺陷**：小说目录走的是 `_findDirectoryEntries` → `Episode.fromRaw(...).toChapter()`，而 `Episode.toChapter()` 把 `volumeName` 写死成 `剧集`：

```dart
Chapter toChapter() => Chapter(itemId: itemId, title: title, volumeName: '剧集');
```

`Episode` 是给短剧用的。小说目录被它解析后，**真实的 `volume_name`（如「第一卷：默认」）被丢弃、版本也无从携带**。改为按来源分流：`episodes` 仍走 `Episode`（短剧，卷名「剧集」），`item_data_list`／`lists`／`item_list` 走 `Chapter.fromRaw`（小说，保留 `volume_name` 与 `version`）。实测 592 章从 0 章有版本变为 592 章有版本，卷名也恢复为真实值。

### 点赞数一直是 0

`parseParagraphComments` 读的是 `data_list[i].stat`，但真实响应把计数器放在 **`data_list[i].comment.stat`** 里。同级那个永远是 `null`，于是每条段评的点赞与回复数都是 0。改为优先读 comment 自己的 `stat`，同时保留同级形式以兼容。顺带补上 `is_author`（来自 `user_info.user_tag`）与 `read_duration`，让面板的「作者」徽章和在读时长有数据。

### 面板按官方版式：单段落的评论列表

版式以用户 2026-09-12 提供的《丹经，丹道，丹圣！》截图为准。反编译代码中的 90% 默认高度和筛选栏属于另一种面板配置，不能据此宣称与这张截图一致。

`ReaderPage._showIdeas` 打开约占可用屏高 **69%**、顶部圆角 **12dp** 的底部面板。`FractionallySizedBox` 按弹窗实际约束计算高度，使横屏和受约束的窗口也保留上方正文。浅色阅读主题使用白色面板，夜间沿用暗色面板。遮罩透明度 0.4，不显示拖动短横条。

标题栏高 56dp，左侧是下拉收起箭头，中央为当前段落的 **N条评论**。打开时用所点气泡的段评数，加载后优先用该段响应总数，不显示整章合计，也不把首批 20 条当作总数。下方直接展示当前段落的评论，删除段落切换条、全部/最新、引用框及分隔线。**2026-09-12：控制栏的「段评 · N」入口已删除**——正文气泡与它信息完全重复（同样显示计数、同样打开面板），菜单只保留目录/夜间/排版/缓存四项；打开面板的唯一入口是正文气泡。

每条评论左侧是 32dp 圆形头像，右侧依次是灰色昵称、16sp 正文、日期与操作信息。日期和「回复」在下方左侧，空心爱心及点赞数、碎心图标在右侧。一天以内显示相对时间，同年旧评论显示 `MM-dd`，往年显示 `yyyy-MM-dd`。正文保持上游顺序，不在客户端重新排序。

后端尚无评论发布、点赞和不喜欢的写接口，心形图标及回复计数作为只读信息展示，不添加虚假点击回调。加载失败提供重试，关闭后到达的异步结果不再更新面板。

### 哪些段落有气泡：只要 `count > 0`

**第一版做错了。** 我读到官方 `CSSParagraphCommentReaderService` 里有：

```java
if (com.dragon.community.impl.d.a.a().a().b() && readerSwitchService().o(...)) {
    paraBubble = (ParaBubble) CollectionKt.getOrNull(paraIdeaData.bubbleData, 3);
    if (paraBubble == null || paraBubble.count <= 0) return;   // 不画
}
int i2 = paraIdeaData.count;                                    // 画的是这个
```

就把 `bubble_data["3"].count > 0` 当成了**无条件门槛**。它在一本测试书上恰好放行 21/48 段，看起来"很合理"，于是没再怀疑。

真机反馈是「怎么只有第一个段落有段评」。回来查那本真机上的书（`茅山鬼术，只杀不度` 第 1 章，36 段）：

| 判据 | 通过段数 |
|---|---|
| `count > 0` | **36 / 36** |
| `bubble_data["1"].count > 0` | 36 / 36 |
| `bubble_data["3"].count > 0` | **1 / 36** |

同一判据在两本书上是 21/48 与 1/36 —— 这种不稳定本身就说明判据错了。回头补看**外层条件**才发现它是 AB 开关：

- `d.a.a().a()` = `lr1.s`，`bp4.a.b()` 的实现是 `ParaCommentFeatured.a.a().enableParaFeatured`；
- 该开关读远程配置 **`para_comment_featured_v697`，默认 `false`**（`mr1.e.b()` 也直接返回 `false`）。

也就是说：**官方默认根本不施加这道门槛**，`count > 0` 就画。

现在的实现：`showsBubble => hasIdeas`。

### 气泡长什么样：官方素材是对话气泡轮廓，不是圆圈（2026-09-12 修正）

**「空心圈」的结论也错了。** 2026-09-12 用户拍板直接采用官方素材，逐像素重查才发现 `cnq` 根本不是圆：它是一个**带尾巴的对话气泡轮廓**——圆角气泡身 + 右上一个勾状小尾巴 + 左下一个小尖角。当初的像素分析只横切了中心行（得到两条 4px 竖线），就把「对称、空心」误读成了「圆环」；`dbe` 是 12dp 的另一种控件，真正的 LIGHT 大档是 `cns`。教训与 39 通道一脉相承：**量到的数据是对的，给形状下结论前要先把蒙版整张画出来看**。

官方视图（`f45/g` + 布局 `cpr.xml`）是 ImageView + TextView 叠放：`f45/f.d()` 选蒙版，**选择依据是段落评论数据的类型而非阅读主题**（`g45/a.b()`：`userCount > 0` → `Type.d()`=1 → `cnq/cnr/cns` 带对勾组；`is_author_comment` → `Type.a()`=2 → `cne/cnf/cng` 钢笔尖组；其余 → `cni/cnj/cnk` 纯气泡组）。三种形状的蒙版均为纯黑 + alpha，运行时用 `p.o(drawable, getGlobalText40Color(theme))` 按阅读主题着色，所以同一蒙版深浅主题通用；View 盒子尺寸取自 `n02/e` 的配置（蒙版 3x 像素 ÷3：plain 24/26/30 方形，users 26×24/28×26/32.3×30，author 26×24/28×26/32×30）。

**第一版也做错了。** 我按"番茄红/暖纸"自己设计了一个**半透明实心灰圆**。用户的第二问是「段评气泡为什么不用番茄小说的」。

于是把官方素材挖出来。皮肤接口 `l94.e` 的默认实现 `m94.d` 把每个方法映射到具体资源 id，逐层解析 `public.xml` 后拿到真实图片：

| 分支 | SMALL | NORMAL | LARGE |
|---|---|---|---|
| `Type.d()` | `drawable/cnq` | `drawable/cnr` | `drawable/dbe` |
| `Type.a()` | `drawable/cne` | `drawable/cnf` | — |
| 其他 | `drawable/cni` | `drawable/cnj` | `drawable/cnk` |

把这些 webp 解码后逐像素分析，三点结论：

1. **它们是纯黑 + alpha 的蒙版，不含颜色** —— 颜色由 `p.o(drawable, color)` 用主题文字色着色（暗色模式下再按 0.6/0.7 调透明度）。所以气泡颜色**应当跟随阅读主题**，不能写死。
2. **是空心圈，不是实心圆**：`cnq` 78×72px 里只有 887/5616 ≈ 15.8% 的像素不透明，横切中心行得到 `4px 描边 → 64px 透明 → 4px 描边`。实心圆该有 ~78%。外层直径 24dp、描边 4px@3x ≈ **1.33dp**。
3. **尺寸分档**（`n02/e.java`）：外径 24 / 26 / 30dp，文字 8 / 9 / 10sp，与正文字号 ≤19 / ≤29 / >29 对应；**间距 8dp**（`ParaBubbleInlineConfig.margin` 的默认值，我第一版用了 6dp）。

`setShowInImage` 只在段落**含图片**时才走另一条 `GradientDrawable`（填充药丸）路径（`b.w()` 由 `a0.c()` 决定），普通文字段落走的就是上面这套图片圈。

数字文案：`q02.a.c()` 在 `getParaBubbleInlineEnable()` 为 false（默认）时用 **≤99 显示原数，>99 显示 `99+`**；开关打开时才改用量级格式。因此实现采用 `99+` 截断。

### 实现方式：气泡进入文本流，不是叠加层

关键决定是**不**把气泡做成覆盖在正文上的独立定位层，而是**排进段落自己的文本流**：把气泡作为 `WidgetSpan` 追加在段落 `TextSpan` 的末尾，并用 `TextPainter.setPlaceholderDimensions` 给它占位。

这样做的好处是命中的是真正的排版结果：

- 气泡天然出现在**末行末尾**，段末放不下时随文本一起换行，不会盖住字；
- 分页测量与绘制用**同一个 span**（`reader_chapter_layout.dart` 里测量用的 `block.span` 就是渲染用的那个），不存在"量出来一个高度、画出来另一个"的偏差；
- 段落内的字一个都没动，气泡纯属追加（有测试断言三段正文仍完整渲染）。

代价与边界：

- 增加了一个 `WidgetSpan`，所以 `\uFFFC` 占位符从 1 个（首行缩进）变成 1~2 个，行内偏移的换算相应调整（`leading` 常量）；
- **"只含气泡的行"不产生切分点**（`cuts` 只在 `starts[i] < text.length` 时新增），因此气泡永远跟着前一行走，不会单独占一页；
- 分页模式下气泡若落在片段被裁切的位置会被 `ClipRect` 裁掉，与正文同一处理，不另做补偿。

### 段评到达要重排版

`_prepareLayout` 原本只在 spec 变化或翻页模式切换时重算布局，而**段评与这两者都无关**。因此加了 `_ideasRevision`：段评变化时 +1，缓存布局记住自己是用哪个 revision 量的，不一致就重算。

这里改动时我自己引入过一个缺陷并被测试当场抓到：重用的判据只看了 spec 与模式，导致段评到达后**直接复用旧布局，气泡永远不出现**（正文正常，只是没气泡——最容易被当成"没数据"的那类静默失败）。修法是把 revision 一并纳入重用条件，同时保住原本"切分页模式不重新测量"的优化。

## 阅读体验批量复刻（2026-09-12，来自官方反编译分析）

对官方反编译源码（`com/dragon/read/ui/menu` + `com/dragon/reader/lib`）做了一轮能力盘点后，一次落地了六项（详见对话记录，此处只记不显然的部分）：

## 听书跟随翻页 + 边走边读（2026-09-12 第二批）

- **听书跟随翻页**（官方 string `aac`「听书进度支持自动翻页」）：`ListeningSession` 单例由听书页发布（book/chapter/position/duration/playing，通知节流 1 秒），阅读器订阅——只有「正在播放且章节匹配」才跟随，暂停不驱动。我们的有声书是**整章一个音频文件**，没有逐句时间戳，跟随只能按比例估算（progress × 页数，瞬时 jump 不做动画追逐）。滚动模式按比例跳 maxScrollExtent。开关在排版面板，默认开。
- **边走边读**（官方 `AudioTtsDepend`：阅读器内 TTS 逐页朗读+自动翻页，走路时计步预测推荐）：用系统 TTS（flutter_tts）实现——「边走边读」按钮从当前页开始朗读，读完自动翻下一页接着读，任何点按/拖动/切章停止。与真人听书页是两条链路（TTS 引擎 vs 音频文件），互不依赖。中文语音依赖设备 TTS 引擎，不可用时提示。
- **教训（又双叒）**：python 无断言的字符串替换会**静默失败**（锚点被 dart format 重排后不匹配），本次「参数已加但按钮没加」排查了三轮；还产生过一个真实换行混进字符串字面量的编译错误，最后用 Edit 工具按精确内容修复。改代码一律 Edit/assert。
- **flutter_tts 与 AGP 9 的兼容**：插件 4.2.5 自带 `buildscript { classpath 'com.android.tools.build:gradle:8.13.0' }`，本项目 AGP 9.0.1 + 国内网络下 dl.google.com 不可达，构建直接失败。修复：补丁 pub 缓存里该插件的 build.gradle——删掉 buildscript 块与 kotlin-stdlib 钉版（宿主已提供 AGP/Kotlin），补丁备份在 `build/validation/flutter_tts-build.gradle.patched.patched`；`pub cache repair` 或升级插件会还原，届时需要重打或升级插件。

## Alternatives considered

- **按 `count > 0` 画气泡（现在采用）**：这正是官方默认行为。第一版因为漏看外层 AB 条件而否掉了它，见上文。
- **保留 `bubble_data[3]` 门槛**：第一版的做法。它让气泡只出现在少数段落上，且在两本书上分别放行 21/48 与 1/36 —— 判据本身不稳定，且与官方默认不符。真机反馈「只有第一段有段评」即由此而来。否掉。
- **面板保持「本章所有段落」列表（第一版）**：实现上只是把已有列表展开，改动最小，但它不是官方面板：官方只展示被点那一段的评论。用户明确要求官方版式，否掉。
- **底部发布栏照官方做出来**：版式更像，但后端没有写接口，点它不会有任何结果 —— 与作者行那个死掉的「关注」按钮同类。缺而不假。
- **保留 90% 高度、段落切换条和全部/最新筛选**：能在弹窗里切换段落和重排评论，但占用了正文与评论空间，且用户给定截图没有这些控件。使用截图中的约七成高度和直接评论列表，上游顺序原样显示。
- **旧缓存没有版本时直接显示空态**：少一次目录请求，但会把元数据缺失误报成没有评论。改为只在缺失时请求目录；代价是首次打开旧缓存的段评多一次网络往返。
- **按正文显示顺序补造段落编号**：无需联网，但标题、空段、插图说明都会改变显示序号，可能把评论挂到错误段落。只从原始 HTML 补回真实编号。
- **每次打开缓存都强制拉正文**：实现简单，但离线缓存和已检查过的正文也要重复联网。采用持久化检查标记，并在有评论需要编号时补取。
- **继续只测桌面后端和 APK 签名**：验证快，但两者都无法发现包内 JNI 库过期。本次核对实际打包库，并将手机内运行的接口作为安装验收的一部分。
- **门槛与显示都用同一个数**：省一层解释，但门槛通道为 0、顶层 `count` 有值的段落大量存在，会与官方数字不符。现在只显示 `count`，问题自然消失。
- **半透明实心圆（第一版外观）**：实现只要一个 `BoxDecoration`，但官方素材实测是**空心圈**，实心圆是另一个控件的样子。用户明确要求番茄样式，否掉。
- **直接引用官方 webp 素材（2026-09-12 起采用）**：曾以版权与换肤过期为由否掉、自绘圆圈替代；用户明确拍板改用官方素材后推翻自绘。现在 `assets/images/bubble/` 内是逐字节原样拷贝的 6 张蒙版（浅色 `cnq/cnr/cns`、夜间 `cne/cnf/cng`），`Image.asset(color: 主题色, colorBlendMode: srcIn)` 复刻官方的运行时着色——形状与官方逐像素一致，颜色仍跟随阅读主题。
- **写死官方浅色皮肤的灰度**：官方颜色来自 `e.D(themeIndex)`，随皮肤与夜间模式变化；写死会在四种阅读背景之一上不可读。改用阅读主题的 `mutedTextColor`。
- **数字用 `1.2万` 量级格式**：那是官方 `getParaBubbleInlineEnable()` 打开后的分支，默认关闭。默认是 `99+`，因此采用 `99+`。
- **把气泡做成正文之上的 `Stack`/`Positioned` 覆盖层**：不必碰 `reader_chapter_layout.dart`，但需要自己按行高算位置，且测量高度与绘制高度会各算一遍；换行、两端对齐、插图、大字号下都要各自处理。选择排进文本流，让排版器负责定位。
- **给非末行也支持气泡**：官方就是末行，且末行定位不需要额外的行内偏移映射。不做。
- **气泡里显示段评正文摘要**：`infos` 实测恒为空（48 段里 46 段为空数组，另 2 段虽带 id 但 `count=0`），正文要再走一跳 `insert_comment_ids`。官方面板里气泡也只有数字。不做。
- **点击气泡跳转段评列表页**：官方是弹面板；本项目已有 `ReaderIdeasSheet`，复用它成本最低，且不新增导航层级。

## Consequences

- 正文里能直接看到哪些段落有讨论及数量；点气泡打开**该段的段评面板**，不需要自己翻找。
- 面板对应用户截图：约七成屏高、左侧收起箭头、居中当前段落评论数，直接展示头像、昵称、正文及底部日期/心形图标。没有底部发布栏（后端无写接口）。
- 面板内不再切换段落或排序；读者通过正文气泡选择另一段。评论列表**下滑到底自动翻页**（2026-09-12 补）：以 `common_list_info` 的 `has_more`／`cursor` 为准，把数字 cursor 回传给 `/api/v1/books/{id}/reviews` 取下一页；首页请求仍不带 cursor，保持配方字节不变。
- **翻页的两段式落地**（2026-09-12 补，回应真机「上下滑动卡顿」）：逐帧测量发现追加一页（setState + 20 行新建布局）在运动中的那一帧耗时 28-41ms，正是用户感到的卡顿。现在请求照旧在页脚进入视野时发出（延迟被滚动过程掩盖），但落地等滚动停止——落地前由页脚转圈提示；落完如果读者仍停在列表尾部会继续喂下一页。另配合头像 `cacheWidth` 按显示尺寸解码、`addAutomaticKeepAlives: false`。逐帧复测：运动中追加尖刺 3→0，最重帧 42ms→7.6ms。翻页状态机是显式四态（idle/fetching/held/failed），在 `_fetchNextPage` 的守卫里 `failed` 允许重试；预取检查必须等下一帧再做（首页加载完成时列表可能尚未构建，`hasClients=false` 会让预取悄悄死掉——这个坑用 dbg 打印才抓到）。
- 气泡是**官方对话气泡轮廓蒙版**（浅色/夜间两套，逐字节来自官方皮肤资源），圈内是数字，颜色跟随阅读主题（运行时 srcIn 着色）；盒子按官方规格 26×24 / 28×26 / 32.3×30dp，间距 8dp，文字 8/9/10sp。
- 标签在 **>99 时显示 `99+`**（官方默认模式的行为）。
- **凡有段评的段落都有气泡**：真机那本书 36 段全部有段评，因此 36 段都会出现气泡（此前只有 1 段）。
- 气泡是段落 `TextSpan` 的一部分，因此**两种阅读模式都自动生效**（分页与滚动），无需分别实现。
- 滚动的 maxScroll、分页的高、插图、位置保存与恢复均未改变语义（既有阅读器测试全绿）。
- 大字号（1.8 倍）与 `99+` 已覆盖，无溢出。
- 段评仍**不影响正文可用性**：加载失败或为空时一个气泡都不画，正文照常。
- **评论正文来自 `server_channel=39`**，面板展示该段真实段评（头像、昵称、时间、正文、赞/回复数、作者徽章）。实测第 32 段 6 条、第 0 段 287 条，计数与 idea 列表逐段一致。
- 阅读器需要章节版本才能列出段评；`Chapter.version` 从目录解析并随缓存持久化。旧缓存没有版本时按需补取；补取失败显示可重试状态，正文仍可阅读。
- 旧缓存缺失段落编号时，有评论的章节首次打开会额外请求一次原始正文；成功后保留编号与检查标记，重新打开复用缓存。离线失败不清空正文，也不显示伪造的评论关联。
- Android 必须随 Dart 改动一起更新 JNI 后端。该库不在 Git 中，构建和安装验收需要额外核对包内版本；只更新桌面可执行文件不会更新手机后端。
- 小说目录改用 `Chapter.fromRaw`，因此**恢复了真实的 `volume_name`**（此前被短剧解析器写成「剧集」）并带上了版本。
- `ParagraphIdeas.showsBubble` 是新的公开判据；`ChapterIdeas.bubbleCounts` 给出「段号 → 显示数字」。
- 气泡增加了一个 `WidgetSpan`，段落测量的占位符数量从 1 变为 1~2，行内偏移换算多了一个常量；这是该方法主要的可读性成本，已就地注明。
